# QmKvm 微服务化高并发架构（唯一交付形态）

> 版本：v2.0（2026-09-07）
> 决策：产品只保留**一个微服务化高并发架构**，不再区分标准版/企业版。
> 理由：单一形态 = 单一维护路径——镜像只有一套、配置矩阵只有一套、文档只有一套；
> "降级版"省下的不是代码，而是两套行为的测试矩阵和销售解释成本。
> 中小客户与超大规模客户跑同一套镜像，差别只在副本数与资源配额。

**与"单体版"的唯一差别**：所有组件都是"多副本 + 分组"的部署方式，代码是同一套。
队列分组、对象存储、读写分离不是企业版专属代码，是默认代码路径。

## 二、服务清单（部署单元）

| 部署单元 | 进程 | 副本策略 | 有状态？ |
|---|---|---|---|
| api | Hono（全路由） | ×2~×N，无粘性 | 否（会话在 Redis） |
| worker-tx | 只订阅 `queue.tx` | 按任务吞吐扩 | 否 |
| worker-notify | 只订阅 `queue.notify` | 独立节奏（短信配额） | 否 |
| worker-supply | 只订阅 `queue.supply` | 凭据隔离域 | 否 |
| worker-ocr | 只订阅 `queue.ocr` | 重 CPU，按图片量扩 | 否 |
| www / portal / admin | 静态产物 | CDN / 对象存储托管 | 否 |
| MySQL 主+从 | — | 1 主 N 从 | 是 |
| Redis Cluster | — | 3 主 3 从起 | 是 |
| 对象存储 | S3 兼容 | 按云商 | 是 |

四个 worker 组是**同一 worker 镜像的不同启动参数**（`--group tx|notify|supply|ocr`），
不是四个代码库——维护面不变，部署面独立。

| 6 | 部署编排 | `docker/docker-compose.cluster.yml` 新建（LB+API×N+worker 分组+Redis Cluster+MinIO 样例） | 1 天 | 附健康检查与扩缩命令 |

这是维护难度不上升的关键。

## 四、实施顺序（一次做完，不设灰度矩阵）

按依赖关系串行：**1 → 2 → 3 → 4 → 5 → 6 → 7**。

- Phase 1（存储+队列+worker 分组）：1→2→3，约 3 天，代码层改动
- Phase 2（OCR+读分离）：4→5，约 2 天，含一次 DB 迁移（0006）
- Phase 3（交付物）：6→7，约 2 天，部署与验证

全程无破坏性变更：迁移脚本保证既有部署数据平滑升级；`ocr_status` 新枚举值向后兼容
（旧值语义不变，`unavailable` 仍表示"不可用/不一致"兜底）。

## 五、维护成本对照（为什么"只留一套"反而更省）

| 维度 | 双版本（单体+集群） | 单一微服务化形态 |
|---|---|---|
| 代码分支/配置矩阵 | 两套（`QUEUE_ROUTING=single\|split`、存储双实现常驻） | 一套：存储固定 S3 兼容，队列固定分组 |
| 测试矩阵 | 单体路径 + 集群路径各测一遍 | 一套 |
| 销售解释成本 | "标准版和企业版的区别是什么" | 演示即解释 |
| 故障排查 | 两种形态两份 runbook | 一份 runbook |

需要放弃的便利：开发环境跑全栈要多起一个 MinIO + worker 分组参数。
对策：`pnpm dev` 保留内嵌本地盘/单队列的开发缺省（env 缺省值即开发态），
**开发态默认值 ≠ 产品形态**——产品默认配置按集群形态出厂，开发本地一键起单进程调试模式。

## 六、对外口径（与代码事实一一对应）

- "微服务化架构：API 无状态多副本 + 四类任务域独立伸缩（交易/通知/供应/OCR）"
- "消息队列解耦（BullMQ），任一任务域故障不阻断交易链路"
- "对象存储承载用户资产，API 完全无状态"
- "单集群支撑百万级注册用户 / 峰值十万级请求（参考架构，见压测报告）"

禁止使用：裸"百万并发"承诺、"任意规模一键扩容"等无对照事实的表述。
所有容量数字以 `scripts/loadtest` 实测报告为准，随交付物一并提供。
